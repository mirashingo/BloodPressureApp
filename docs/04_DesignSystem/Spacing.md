# Spacing

DS-SPACING-001

## 名称

スペーシングデザインシステム

------------------------------------------------------------------------

## 1. 目的

本書は、BloodPressureApp 全体で使用する余白、間隔、内側余白の基準を定義する。

Spacing Token を統一することで、画面ごとの余白のばらつきを防ぎ、スマートフォン縦画面を中心に、見やすく、押しやすく、読みやすい UI を維持する。

本書は、P3-03 Design Tokens 実装における AppSpacing の仕様正本とする。

------------------------------------------------------------------------

## 2. 基本原則

- 4dp グリッドを基本とする。
- `space2` は微調整用途に限定する。
- 画面内で任意の Spacing 値を直接指定しない。
- 固定 Height と Spacing を混同しない。
- Text Scale 200% でも文字が切れない構成を優先する。
- SafeArea と MediaQuery を考慮する。
- スマートフォン縦画面を基本とする。
- Spacing は余白、間隔、Padding、Gap のために使用する。
- Component の最小高さやタップ領域は、Spacing ではなく Component Size の責務とする。

------------------------------------------------------------------------

## 3. Token 一覧表

| Token | 値 | 主な用途 |
|---|---:|---|
| `space2` | 2dp | 4dp では大きすぎる場合の微調整 |
| `space4` | 4dp | 非常に近い要素間の最小間隔 |
| `space8` | 8dp | 関連要素間、ラベルと入力欄の間 |
| `space12` | 12dp | ボタン内上下余白、やや小さめの内側余白 |
| `space16` | 16dp | 画面左右余白、カード内余白、フォーム項目間、一覧項目内余白 |
| `space20` | 20dp | `space16` より少し広く、`space24` ほど分離しない間隔 |
| `space24` | 24dp | セクション間、ボタン内左右余白 |
| `space32` | 32dp | 大きな内容ブロック間の余白 |
| `space40` | 40dp | 主要領域同士を大きく分離する余白 |
| `space48` | 48dp | 最も大きな余白、画面内の強い区切り |

------------------------------------------------------------------------

## 4. Semantic Usage 一覧

| Semantic | 使用 Token | 用途 |
|---|---|---|
| `screenHorizontalPadding` | `space16` | 画面左右余白 |
| `sectionGap` | `space24` | セクション間の縦方向余白 |
| `cardPadding` | `space16` | カード内余白 |
| `relatedItemGap` | `space8` | 関連要素間の余白 |
| `formFieldGap` | `space16` | フォーム項目間の余白 |
| `labelInputGap` | `space8` | ラベルと入力欄の間 |
| `buttonHorizontalPadding` | `space24` | ボタン内左右余白 |
| `buttonVerticalPadding` | `space12` | ボタン内上下余白 |
| `listItemPadding` | `space16` | 一覧項目内余白 |

Semantic Usage は、画面実装時の判断基準とする。

同じ Token 値であっても、意味が異なる場合は用途名を分けて扱う。

------------------------------------------------------------------------

## 5. 画面余白

画面左右余白は `space16` を標準とする。

画面端の余白は、SafeArea と MediaQuery による端末固有の余白を考慮した上で、コンテンツ領域に対して適用する。

スマートフォン縦画面を基本とし、横幅の狭い画面でも主要な入力、ボタン、血圧値表示が窮屈にならないことを優先する。

Text Scale 200% 時に文字が切れる場合は、固定高さを増やすのではなく、折り返し、縦方向の伸長、スクロール可能な構成を優先する。

------------------------------------------------------------------------

## 6. Card・List・Form・Button での使用方針

### Card

- カード内余白は `space16` を標準とする。
- カード内で関連する要素の間は `space8` を標準とする。
- カード同士、またはカードと別セクションの間は `space24` を標準とする。

### List

- 一覧項目内余白は `space16` を標準とする。
- 一覧内のラベル、値、補助テキストの間隔は、関係性に応じて `space8` を基本とする。
- 一覧項目の高さは Spacing Token だけで固定しない。

### Form

- フォーム項目間は `space16` を標準とする。
- ラベルと入力欄の間は `space8` を標準とする。
- 入力欄の高さや最小タップ領域は、Spacing ではなく Component Size と Accessibility の方針に従う。

### Button

- ボタン内左右余白は `space24` を標準とする。
- ボタン内上下余白は `space12` を標準とする。
- ボタンの最小高さは Spacing ではなく Component Size の責務とする。

------------------------------------------------------------------------

## 7. Responsive Design

Spacing はスマートフォン縦画面を基準に定義する。

タブレット、横画面、Windows/Desktop 表示では、画面幅に応じてレイアウトの最大幅、カラム構成、スクロール領域を調整する。Spacing Token 自体に未定義の値を追加しない。

広い画面で余白が必要な場合も、本書で定義した Token を組み合わせて使用し、画面ごとに任意の値を直接指定しない。

SafeArea、キーボード表示、システム UI、MediaQuery の Insets を考慮し、入力フォームや主要ボタンが隠れないようにする。

------------------------------------------------------------------------

## 8. Accessibility

- Text Scale 200% でも文字が切れないことを優先する。
- 色や余白だけで状態を伝えない。
- 高齢者を含む利用者が読みやすい余白を確保する。
- タップ領域の確保は Component Size と組み合わせて確認する。
- 余白を詰めすぎて、入力欄、ボタン、血圧値、エラー表示の関係が分かりにくくならないようにする。
- 画面の情報量を増やすために、独自の小さい余白値を追加しない。

------------------------------------------------------------------------

## 9. Flutter 実装時の命名例

将来の Flutter 実装では、次の配置を使用する。

`lib/design_system/tokens/app_spacing.dart`

命名例は次のとおりとする。

| 種別 | 命名例 |
|---|---|
| Class | `AppSpacing` |
| Token | `AppSpacing.space16` |
| Semantic 名 | `screenHorizontalPadding`, `sectionGap`, `cardPadding` |

P3-03 では Token 定義を実装し、P3-04 では ThemeData や各 Component から参照する。

------------------------------------------------------------------------

## 10. 禁止事項

以下を禁止する。

- 画面内で任意の Spacing 値を直接指定すること
- 本書にない Spacing Token を独自追加すること
- `space2` を通常のレイアウト余白として多用すること
- 固定 Height の代替として Spacing Token を使用すること
- Text Scale 拡大時に文字が切れる固定高さレイアウトを優先すること
- SafeArea や MediaQuery を無視して画面端へ要素を配置すること
- Feature ごとに独自の Spacing Scale を定義すること
- Design System を通さずに、共通 Component と同等の余白を画面ごとに再定義すること
